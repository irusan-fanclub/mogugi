# Release note 撰寫準則（給 agent）

MOGUGI 的 release note 是寫給**一般玩家**看的，不是給開發者。使用者反覆要求「簡單、看得懂」。發布前一定要先把草稿給使用者看過再送出。

## 讀者是誰

- 玩魔力寶貝、會用這個傷害計量器的一般玩家。
- 他們**不懂也不想知道**：封包 opcode、欄位型別、函式／檔案名稱、entity id、race id、commit sha、TDD、重構。
- 他們**想知道**：這版對我有什麼差別？哪個數字以前是錯的、現在對了？有沒有我該注意的地方？

## 格式

```
# MOGUGI vX.Y.Z

### <emoji> <分類標題>
- <一條具體、使用者看得到的改變>
- <...>

### <emoji> <另一個分類>
- <...>
```

- 標題固定 `# MOGUGI vX.Y.Z`。
- 用 emoji 開頭的分類標題把改動分組（例：🎭 人偶傷害、🎒 物品索引、🗺️ 副本偵測、🔐 啟用系統、📡 即時捕捉、📦 遊戲資料更新、🐛 修正）。
- 每條一個 bullet，講一件使用者感受得到的事。
- 一律**繁體中文**。

## 寫法

**要：**
- 用玩家的語言描述現象與結果。
  - 好：「人偶打出的傷害現在會算進主人的輸出，之前完全沒有被計算。」
  - 壞：「透過 0x9025 封包將 marionette entity 綁定到 summoner。」
- 有助理解時，給**具體影響數字**。
  - 「實測一場戰鬥，人偶玩家有 75% 的傷害漏算。」
- 該版若有**已知限制**且會影響使用者，用一兩句誠實寫出來。
  - 「若人偶在你看到它之前就已召喚出來，該人偶的傷害仍無法對應到主人。」
- 分類順序：最重要、影響最大的放最前面。
- 保持精簡。整份能一眼看完最好。

**不要：**
- 不要出現技術內部名詞：opcode、封包、entity/race id、type 318、函式/檔名、commit、reattribute、placeholder…（要講也要翻成玩家聽得懂的話）。
- 不要寫實作細節與過程（「用 TDD」「重構了 X」「回測三份錄製」屬於 commit message，不是 release note）。
- 不要放 emoji 以外的裝飾；不要長篇大論。
- 不要把 bugfix 寫得像沒事發生 —— 若某數字以前是錯的，直說。

## 版號

- 遵守 semver，且**不可低於已發布的最新版**。開 release 前先 `git tag --sort=-v:refname | head` 或 `gh release list` 確認目前最新版。
- 純修正 → patch（0.4.0 → 0.4.1）。新功能／行為明顯改變 → minor（0.4.x → 0.5.0）。
- 使用者若口頭給了一個會造成倒退的版號（例如目前已 0.4.0 卻說要 0.3.1），先提醒再依其決定。

## 發布流程（參考）

1. `release.ps1` 產生 `dist/mogugi_<version>.exe` 與 `.zip`（前端＋後端＋內嵌資料）。
2. **先把 release note 草稿貼給使用者確認。**
3. `git tag vX.Y.Z` → `git push github master` → `git push github vX.Y.Z`。
4. `gh release create vX.Y.Z <exe> <zip> --title "vX.Y.Z" --notes-file <note>`。
5. GitHub release published 會觸發 Discord 公告 workflow（`discord-release.yml`）自動發到社群。
   - zip 超過 8 MB 時 Discord 只發純文字 embed＋下載連結，不附檔（正常行為）。
   - Discord 訊息由 webhook 發出，**無法事後編輯或刪除**；notes 要在發布前就定稿。

## 範本（v0.4.0，符合本準則）

```
# MOGUGI v0.4.0

### 🎭 人偶傷害(修正)
- 人偶打出的傷害現在會算進主人的輸出，之前完全沒有被計算。
- 實測一場戰鬥，人偶玩家有 75% 的傷害漏算。
- 人偶傷害視為玩家本人的輸出，DPS 圖表也會一起計入。
- 若人偶在你看到它之前就已召喚出來，該人偶的傷害仍無法對應到主人。

### 🧹 物品索引
- 人偶、召喚物不再產生多餘的資料。

### 📦 遊戲資料更新
- 更新至 tw v159，新的人偶技能名稱皆可正常顯示。
```
